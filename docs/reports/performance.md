The camera path works end to end in Chromium. A real issued code goes through simulated hand-held phone video, the fake capture device, the production web build, the decoder Web Worker, `POST /api/v1/verify` and the result view, which shows AUTHENTIC with product id O26-J-00184. A forged code is shown as INVALID SIGNATURE. Declined or blocked camera access shows the fallback screen, and uploading a photo from that screen verifies the code.

## 1. End-to-end camera scan (real browser)

### Method

```
issued product O26-J-00184 (real issuance: Ed25519 signature, registry rows)
  → core encoder + SVG renderer → resvg raster (800 px)
  → camera simulator: hand-held portrait 720×1280 video, typicalPhone conditions
    (perspective, barrel distortion, clutter, paper texture, uneven light,
     vignetting, defocus 0.85 px, sensor noise, JPEG 85), 8 frames of slow
     periodic motion (±14 px, ±1.2° roll, ±2° tilt, shake blur every 3rd frame)
  → Y4M (C420, limited range, 15 fps) → Chromium --use-fake-device-for-media-stream
    --use-fake-ui-for-media-stream --use-file-for-fake-video-capture=<clip>
  → /verify built by `scripts/build-web.ts --out <tmp>` (the real CLI, production mode)
    and served by buildApp() listening on 127.0.0.1:<ephemeral>, PGlite, seeded catalogue
  → phone context 390×844 CSS px, deviceScaleFactor 3, isMobile, hasTouch
  → tap SCAN ORBES CODE → decoder worker → POST /api/v1/verify → result view
```

Timing is taken on the page clock by an init script (`INSTRUMENTATION` in `test/e2e/support.ts`). The script wraps `getUserMedia` and `Worker.postMessage`, listens to worker replies, records taps, and observes `body[data-screen]` and the scan lock. Definitions:

- **recognition**: `getUserMedia` called (camera start) → first successful decode reply on the main thread. It covers device start, `play()`, the first video frame, the reticle crop, the transfer, and the worker decode. This is the < 1 s target.
- **live → decoded**: the same, but starting from the moment the stream is live.
- **time to result**: tap on SCAN ORBES CODE → result screen mounted. It includes the `/verify` round trip over real HTTP on loopback.

Two motion settings were measured:

- **Reduced motion** (`prefers-reduced-motion: reduce`) removes the deliberate UI pauses: the 280 ms screen fade, the 420 ms lock pause and the 650 ms minimum VERIFYING… display. This isolates the pipeline.
- **Designed motion** keeps those pauses.

Before any browser runs, the test checks in Node that every steady frame of each clip decodes and that every "arriving" frame does not. This makes "frames to recognition" a property of the clip.

### Fake-camera calibration (`fake-camera.test.ts`)

A 13-level gray ramp was played through getUserMedia → `<video>` → canvas:

- **`limited`** (the default of `test/support/y4m.ts`): the page sees the source levels within ±1 (max error 1), with neutral chroma, at the file's size and frame rate. This is the range to use.
- **`full`**: Chromium still treats Y as BT.601 video range. It expands `(Y−16)·255/219`, so levels ≤ 16 become black and levels ≥ 235 become white. Colours are not washed out, but contrast is stretched and both ends clip. Both ranges decode (table above), and the calibration test asserts each mapping.

## 2. Decoder latency (`bench.ts` a)

**Method.** The frames are 1 280×720, generated in Node:

- 24 frames with a code: distinct real CODE-01 artifacts (`test/decoder/fixtures.ts`) under the camera simulator's `typicalPhone` preset at 8 px/unit, with a random pose (any rotation, tilt ±12°, offset).
- 12 code-free frames: a blank tag on a cluttered desk, with the same conditions.

Both environments run the web app's own frame step (`frame-decoder.ts`: RGBA → luma → `decodeOrbesCode` with the camera options: inverted on, mirrored off, genome on):

- **Node**: wall time of `handleDecode`.
- **Chromium**: the production decoder worker (`src/web/verify/worker.ts` bundled by esbuild with the web build's targets, 56.6 KB). Frames are fetched as bytes, expanded to RGBA in the page, then a fresh buffer is **transferred** per decode like the scanner does. Timing is the page → worker → page round trip.

Each environment does 6 warm-up decodes, then 3 repetitions of each frame. All 216 decodes per run were correct: every code read with the right bytes, and no code reported on the code-free frames.

| environment | frames | p50 | p95 | max | of which decode p50 | RGBA→luma p50 |
|---|---|---|---|---|---|---|
| Chromium worker | with a code | 46.1 / 52.9 ms | 94.4 / 102.4 | 125.8 / 201.1 | 30.4 / 35.7 | 13.4 / 14.8 |
| Chromium worker | code-free | 184.9 / 155.1 ms | 370.4 / 305.6 | 524.8 / 332.0 | 168.1 / 135.4 | 15.0 / 13.4 |
| Node 22 | with a code | 72.4 / 45.8 ms | 162.0 / 77.5 | 259.8 / 104.0 | 56.0 / 33.8 | 15.0 / 11.2 |
| Node 22 | code-free | 287.2 / 168.8 ms | 639.6 / 260.1 | 694.8 / 260.9 | 257.8 / 155.7 | 18.1 / 11.5 |
| cold first frame (fresh worker / process) | | Chromium 348 / 331 ms · Node 394 / 251 ms | | | | |

Values are given as run 1 / run 2.

These are **whole 1280×720 frames**. The live scanner sends only the square under the reticle (478–566 px on this phone viewport, at most 960 px), so its per-frame work is smaller. In the E2E runs, worker decodes of a cold worker's first frame took 173–792 ms under load.

## 3. Verify API latency (`bench.ts` b)

**Method.**

- **Context.** `createContext` + `buildApp` (the server's real wiring: rate-limit plugin, cookies, helmet, zod, services) on `pglite:memory`. Requests go through `app.inject`, so there is no socket and no network.
- **Seed.** 100 products: 40 issued, 30 sold (warranty activated, unregistered), 20 owned (registered through the real token flow) and 10 with a superseded code.
- **Measured.** After 50 warm-up requests, 1 000 **sequential** requests, then 1 000 more with **8 in flight**.
- **Request mix.** Seeded:
  - 90 % genuine codes, carrying the genome reading and the client metrics the web app sends;
  - 5 % invalid signatures (flipped bit, valid CRC);
  - 5 % malformed codes (broken CRC).
  - Traffic comes from 30 devices holding server-issued `orbes_device` cookies, behind 40 client addresses.
- **What each request does.** Each one persists a scan event, an authentication event, anomaly evaluation over the code's scan history and, where it applies, a first-registration token.

| PGlite | n | p50 | p95 | p99 | max | throughput |
|---|---|---|---|---|---|---|
| sequential, run 1 | 1 000 | 16.6 ms | **28.6 ms** | 36.4 ms | 50.2 ms | 55 req/s |
| sequential, run 2 | 1 000 | 18.2 ms | **32.0 ms** | 39.9 ms | 76.3 ms | 51 req/s |
| 8 in flight, run 1 | 1 000 | 136.6 ms | 222.6 ms | 251.0 ms | 268.8 ms | 54 req/s |
| 8 in flight, run 2 | 1 000 | 148.2 ms | 222.8 ms | 260.7 ms | 307.8 ms | 52 req/s |

- **States returned (sequential run):** AUTHENTIC 369, FIRST_REGISTRATION 271, REGISTERED 173, REVOKED 87, INVALID_SIGNATURE 50, MALFORMED_CODE 50. There were no non-200 answers.
- **p95 by kind:** genuine 27–34 ms; invalid signature 10–23 ms; malformed 9–13 ms. The last two stop before any registry or history query.
- **Concurrency on PGlite.** PGlite is a single in-process connection, so 8 in flight gives **no extra throughput**. The latency then counts queueing (≈ 8 × the service time). This is the expected behaviour of the dev/test database and not a property of the service. With 8 in flight the p99 was 251–261 ms and one request reached 308 ms, just over the 300 ms target. That figure is queueing on one connection, not service time.
- **PostgreSQL 16.** Not measured, see Limitations.

## Observations and recommendations

1. **The cold worker is the largest avoidable cost in recognition.** The first decode in a fresh worker or process takes 250–390 ms in the benchmark and 173–792 ms in the E2E scans, under load. Warm decodes of a full frame take 46–53 ms p50. The app already boots the worker at idle time, but it does not exercise the decoder. One synthetic decode at idle on the landing page would JIT-warm the decoder before the visitor taps SCAN, for example a small built-in frame. By our estimate (cold minus warm decode), this could remove about 200–300 ms from the first recognition. That saving is unmeasured. Owner: verify web app (`src/web/verify/main.ts`, `scanner.ts`). Not changed here. **Implemented (2026-10-01):** the landing page now decodes one tiny synthetic code (200 × 200 px, the public sample vector, `src/web/verify/warmup.ts`) at idle through `DecoderClient.warm()`. Measured in the E2E camera file (4 fresh reduced-motion scans each, load 0.4–0.6 per CPU): warm-up decode 71–91 ms on the landing page; the first camera frame then decodes in 63–113 ms (median 81) against 103–146 ms (median 119) without the warm-up, and time-to-recognition falls from a median of 305 ms to 267 ms. The saving is larger under load, where cold first decodes reached 792 ms.
2. **Frames without a code cost 3–4× more than frames with one.** p50 is 155–185 ms against 46–53 ms in the worker, because the finder exhausts its seal candidates. While nothing is in view, the scanner therefore runs at about 3–6 frames/s rather than the 8 frames/s that the 120 ms cadence allows (E2E blank tag: 21–40 frames in about 6.8 s). This is acceptable and battery-friendly, but it is the case to optimise if the frame rate ever matters.
3. **Guidance on a code-free view says "Move a little closer".** Every code-free frame (36/36 decodes in each benchmark environment, and every reply in the three E2E runs) fails with `NO_MOONS`, never `NO_SEAL`. The decoder finds a seal candidate somewhere in the desk clutter and reports "no code structure around the seal". Only a featureless frame gives `NO_SEAL`. `scanHint()` maps `NO_MOONS` to *closer*, so a visitor pointing at the wrong thing is told to move closer instead of *Place the whole code inside the orbit*. This is minor UX copy and logic in `src/web/verify/capture.ts` and the decoder's failure ranking. It is reported, not changed. The E2E test accepts either hint. **Implemented (2026-10-01):** failures now carry seal evidence (share of data orbits with arc texture around the seal) and the scale of a located code; hints follow the prevailing failure of the last six frames. A code-free view gets *Place the whole code inside the orbit* (asserted exactly by the fallbacks E2E test), and "Move a little closer" is gone: a code too small to read gets *Zoom in* or *Hold about 20 cm away* (`src/web/verify/capture.ts`).
4. **Chromium crops a 720×1280 fake camera to 720×1080.** The app asks for an ideal 1920×1080, and Chromium crops the portrait clip to the ideal height. The reticle is centred, so nothing it needs is lost. This is the behaviour of desktop Chromium's fake device. Phone browsers apply constraints in sensor orientation and were not tested.
5. **The server's own verify time.** Seen from the browser, `scan_events.latency_ms` was 28–34 ms (156 ms during a load spike). This is consistent with the API benchmark.

## Limitations

- **Shared, loaded VM.** The E2E camera file ran 3 times and the benchmarks twice, on 4 virtual CPUs while other suites ran. There was no CPU pinning, no frequency control and no isolation. Sample sizes are small: 3 × (4 + 5) E2E camera scans, and 72/36 decodes per environment and run. The distributions are indicative, not statistically tight.
- **A fake camera is not a phone camera.** Chromium plays a prerecorded, already-focused Y4M at 15 fps. Absent are autofocus and exposure convergence (often 0.3–1 s on real devices), real sensor noise, ISP sharpening, rolling shutter, torch, zoom, thermal throttling, and the device's own getUserMedia start-up time. Recognition here measures **our pipeline**, from camera start to the decoded frame, not a phone's camera stack. The simulated video is hand-held and degraded (see Method), but every steady frame is readable, so the first frame sent is read. Recognition here therefore never includes searching or refocusing, except in the settling clip.
- **The CPU is a desktop Xeon core.** Recent flagship phones may decode faster, and mid-range Android phones may be several times slower. Neither was measured. A real-device run, for example over remote debugging, is still needed before the 1 s target can be claimed on phones.
- **Headless Chromium on Linux** composites in software. Safari/WebKit and Firefox were not measured.
- **No network.** The API numbers use `app.inject`, as the target specifies (excluding network). The E2E `/verify` call crosses loopback HTTP only.
- **PostgreSQL 16 was not measured.** This session had no credentials for the local server: `ORBES_TEST_POSTGRES_URL` was not set, and no role was available to it. The benchmark creates a throwaway database, runs the same seed, API and issuance workloads, and drops the database. That code path mirrors `test/api/postgres.test.ts` but **has not been executed**. To fill the gap: `ORBES_TEST_POSTGRES_URL=postgres://<role with CREATEDB>@127.0.0.1:5432/postgres npx tsx scripts/bench.ts --only api,issuance`.
- **Assertions are deliberately tolerant.** The E2E tests assert:
  - correctness: states, product id, nothing disclosed on invalid codes, permissions, camera release;
  - "read on the first or second frame sent";
  - a 6 s per-scan ceiling;
  - the 1 s target on the best of 4 runs, but only while the load is below 1.5 per CPU. Above that the target is recorded, not asserted. `ORBES_E2E_STRICT=1` enforces it on the median.

  A slow regression on a busy CI could therefore pass. Watch `genome/out/e2e/camera-scan.json`.
