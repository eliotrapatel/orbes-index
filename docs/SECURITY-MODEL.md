# ORBES GENOME CODE™ — Security Model

Status: v0.1. Companion documents: [THREAT-MODEL](THREAT-MODEL.md) (what we defend against) and [CRYPTOGRAPHY](CRYPTOGRAPHY.md) (primitives and formats).

## 1. Principles

1. **Established cryptography only.** Ed25519, SHA-256, HMAC-SHA-256, scrypt and AES-256-GCM, all from `node:crypto` or the audited `@noble/*` libraries. No home-made primitives.
2. **No security through obscurity.** The code format, the Genome permutation, the source code and the public keys are all assumed public. The only secrets are the private keys, server-side peppers and secrets, and user credentials.
3. **The server decides.** Browsers decode codes for speed. The server re-validates every byte and makes every decision.
4. **Separate identity from authentication.** The Genome is public identity. The signature is the proof of issuance. Ownership and lifecycle are registry state, so changing them never touches the cryptographic identity.
5. **Honest outcomes.** The public states describe exactly what was verified. They never claim the physical object is genuine.
6. **Minimise personal data.** Codes contain no personal data. Scan telemetry is pseudonymous (HMAC), coarse and purpose-bound.
7. **Defence in depth with auditability.** Every privileged mutation is audited in a tamper-evident hash chain.

## 2. What a verification proves

| Layer | Check | Proves |
|---|---|---|
| A. Authentic code | Ed25519 signature by an ORBES key over the canonical payload | The data was issued by ORBES. |
| B. Registered product | The identity, code issue and payload hash match the registry | The code corresponds to a product ORBES recorded. |
| C. Valid status | The product and code are not revoked, retired or counterfeit-flagged | The identity is currently active. |
| D. Lifecycle consistency | Ownership, warranty and transfer state | The scan is consistent with the product's history. |
| E. Anomaly detection | Scan-pattern rules and risk score | No suspicious duplication or travel is currently detected. |

None of these layers proves that the scanned object is the original physical item. Hardware binding (see [FUTURE-HARDWARE](FUTURE-HARDWARE.md)) is the planned path towards that.

An **ownership certificate** (F-06, API §8.7) proves less still: that, when it is read, the ORBES registry records the piece it names as registered to an account (verified or not), under warranty or not, with no loss or theft reported. It says nothing about the object it is shown with, and never says AUTHENTIC: a buyer checks the object by scanning its ORBES CODE, and receives it through the transfer bound to that scan (API §11.3).

## 3. Controls catalogue

### 3.1 Cryptographic controls
- **Signing:** Ed25519 (RFC 8032, pure). Domain-separated message: `"ORBES-CODE/v1" ‖ 0x00 ‖ payload`.
- **Verification:** `node:crypto`. Verification fails if the signature is not exactly 64 bytes or the key is not exactly 32 bytes. Malformed inputs never throw past the verification boundary.
- **Weak keys:** one strict rule, `isStrictEd25519PublicKey` in `src/server/crypto/ed25519-node.ts` (canonical encoding of a point of order > 8), is applied by `verifyEd25519Node` before OpenSSL and by `KeyService` before it registers any key: small-order and non-canonical keys (with which `R = identity, S = 0` verifies for every message) can neither verify nor be registered.
- **Key ids:** a 1-byte key id is carried in every code and resolved only through the `cryptographic_keys` registry. Unknown ids give `INVALID_SIGNATURE`.
- **Verify-after-sign:** every signature produced at issuance is verified with the registered public key before it is stored.
- **Key states:** ACTIVE (one at a time, enforced by a partial unique index), RETIRED (verify-only) and REVOKED (with `compromised_at`). Codes registered before the compromise remain trusted. Anything else signed by a revoked key — a later code, or an identity ORBES never registered — fails with `INVALID_SIGNATURE`: the revoked-key rule runs right after the signature check, before the registry lookup can answer `UNKNOWN`. The public key list publishes `revokedAt` and `compromisedAt` (never the reason).
- **Decision order:** parse → key lookup → signature → revoked-key trust → genome-version support → registry → genome cross-check → statuses → anomalies → ownership → authenticators (PLATFORM-CONTRACTS §2.4). Every signed field is authenticated before it is interpreted: an edited genome version is `INVALID_SIGNATURE`; only a *validly signed* unsupported version is `UNKNOWN` (server outdated, logged).

### 3.2 Key custody
- `KeyProvider` interface: `generate`, `sign`.
  - `LocalKeyProvider` (development and small deployments): Ed25519 seeds encrypted with AES-256-GCM under `KEY_ENCRYPTION_KEY`, with the kid as AAD. Directory mode 0700, files 0600. Integrity-checked on load.
  - `MemoryKeyProvider`: tests and demo only. Refused when `ORBES_ENV=production`.
  - A KMS/HSM provider implements the same two methods. The private key never leaves the KMS.
- Private keys never appear in the database, logs, API responses, frontend bundles or generated codes.

### 3.3 Authentication and sessions
- **Passwords:** scrypt (N = 2¹⁵, r = 8, p = 1), 16-byte salt, 32-byte output, constant-time comparison, minimum 12 characters.
- **Customers:**
  - Per-account login throttle: after 10 wrong passwords within 15 minutes, logins to that account are refused for the rest of the window without checking the password, with the same `INVALID_CREDENTIALS` answer and timing as a wrong password (no lockout oracle, no enumeration). It complements the per-IP `auth` rate limit, which a distributed guesser can spread across addresses.
  - **Accepted:** registration answers `409 EMAIL_TAKEN` for an existing email, which lets a caller test whether an email has an account. Without an email channel (no verification or reset mail exists yet) registration cannot answer both cases alike; the `auth` rate limit bounds the probing rate. Revisit when email verification is added.
  - **Password change** (`POST /api/v1/account/password`, C-04): the current password is required. A wrong one answers `400 CURRENT_PASSWORD_INVALID`, never a 401 (the apps end the session on any 401), and counts in the per-account login throttle above, so a stolen session cannot guess the password faster than a login; while the account is throttled the current password is not checked. The change ends every other session of the account and keeps the caller's. The two scrypt evaluations run before the write, which then re-reads the account under its row lock and writes only if nothing happened meanwhile: an account LOCKED since answers `403 ACCOUNT_LOCKED`, a caller's session ended since (by a recovery or a lock) `401`, a password replaced since (by a recovery or another change) `400 CURRENT_PASSWORD_INVALID`. So whoever holds a hijacked session and the old password cannot undo a recovery by changing the password while it commits.
  - **Assisted recovery** (C-04). There is no email channel, so a forgotten password goes through ORBES Client Services:
    - after an **identity check** (the procedure is written with counsel), an ADMIN issues a one-time recovery code in the console (`POST /api/admin/owners/:id/recovery-code`, audited `account.recovery_code.issue`). It is 12 Crockford base32 characters (60 bits), shown once and stored only as an scrypt hash (`account_recovery_codes`), valid **30 minutes** (`RECOVERY_CODE_TTL_MS`: one delay for every recovery code, the shorter and safer of the two briefs that asked for it), used once, one open per account (a new code revokes the previous one; a partial unique index enforces it), never in the audit log, and only for an ACTIVE account;
    - the customer enters it on /verify with a new password (`POST /api/v1/account/recover`, session-less, origin check, `auth` rate group). The same `400 RECOVERY_CODE_INVALID`, at the same cost (one scrypt), answers an unknown email and a wrong, malformed, expired, used or replaced code: no account enumeration. At most 5 wrong guesses at the open code per rolling hour, counted from the audit log (`account.recover_failed` entries naming the code) under the account's row lock, so the limit holds across instances; then even the right code is refused for the rest of the hour, which outlasts the code. An attempt while no code is open, or once it has expired, guesses nothing: it is recorded with its reason (`NO_OPEN_CODE`, `EXPIRED`) and costs the same scrypt, but spends no budget, so a code freshly issued always starts with its 5 guesses (the budget is per code, not per account as the brief had it: a per-account count would let whoever knows the email spend every new code's budget in advance). Those attempts are bounded only by the per-client `auth` rate limit, so their scrypt runs after the attempt's transaction commits: a burst naming one email holds neither the account's row lock (sign-in and transfers take it too) nor a pool connection (shared with /verify) while it hashes;
    - in one transaction the recovery stores the new password, **ends every session of the account**, **cancels its pending transfers**, **withdraws its open links to ownership certificates** (F-06) and **pauses new transfers out of it for 72 hours** (`accounts.transfers_frozen_until`, `409 TRANSFERS_PAUSED`). Whoever obtained a code by impersonating the customer can neither keep a session they had nor hand the pieces on at once; whoever held the account before the customer recovered it loses the certificate links they shared; the real customer, who still has their pieces registered, reaches Client Services within the pause. Conversely, after a recovery by the customer, nothing that was under way with the old password survives it: a sign-in re-reads the password hash under the account's row lock before it opens a session (and writes a re-hash only if the hash is unchanged), and a password change re-reads it before it writes (above), so neither opens a session nor sets a password once the recovery has committed. A LOCKED account is refused (`403 ACCOUNT_LOCKED`) even with the right code, and the lock revokes the open code (below);
    - **Accepted:** someone who knows a customer's email and hammers the form during the 30 minutes after Client Services issued a code can spend that code's 5 guesses before the customer types it; the code is then refused for the rest of its life, and Client Services, who see *Recovery attempts throttled until …* on the owner's record and the `account.recover_failed` / `account.recover_throttled` entries naming the code, issue a new one, which starts afresh. The attacker has to repeat it within each new code's 30 minutes, which needs to know when a code was issued; attempts outside those windows spend nothing. The identity check is a human process, and the pause, the audit trail (`account.recover`, naming the account, never the email or the code) and the 30-minute life of a code bound what a mistake in it can cost.
  - **Loss and theft** (F-01, MY PIECES): the owner reports a piece LOST or STOLEN without scanning it (`POST /api/v1/ownership/incidents`), and withdraws only a loss they reported themselves (`POST /api/v1/ownership/incidents/resolve`, audited `ownership.incident.resolve`): the last move of the piece's status history, into LOST, must be this account's. A STOLEN, or a LOST recorded by ORBES Client Services, is withdrawn by staff once they have checked the piece, so whoever takes over an account after a theft (a hijacked session, a recovery obtained by impersonation, THREAT-MODEL U) cannot make the stolen piece read as clean again. The withdrawal also asks for the **account's password, typed again** (PIECE FOUND, rate group `auth`): a session alone, left open on another device or taken over, does not make a lost piece read as clean; a wrong password is `400 CURRENT_PASSWORD_INVALID` and counts in the account's sign-in throttle (`account.login_failed`, `via: "incident_resolve"`), as the current password of a password change does. The report itself ends no session. Residual risk: whoever holds the password (a takeover by phishing, or by a recovery obtained by impersonation) can still withdraw a LOST the owner declared, audited `ownership.incident.resolve` and visible on the owner's sheet; an owner who suspects a theft declares STOLEN, which only ORBES Client Services lift (THREAT-MODEL U). A declaration is refused where the lifecycle would refuse it (a piece revoked, retired or flagged by ORBES, or already reported: `409 INCIDENT_NOT_ALLOWED`, said of the piece and naming no status), and MY PIECES does not offer it there (`incidentReportable`). Both routes are the current owner's only, answer a stranger and an unknown id alike (`403 NOT_OWNER`), and re-read the account under its lock (a LOCKED account is refused).
  - **A transfer is received for the piece scanned** (F-03, API §11.3): a transfer code is accepted only with the piece the recipient scanned (`productId`) and the `TRANSFER_ACCEPT` token of that scan, which `POST /api/v1/verify` gives a signed-in account that does not own a piece whose transfer is pending, on an authentic result, or on UNUSUAL ACTIVITY from the scan history alone (the registration's exception: strangers scanning copies of a code shown in a listing must not lock the recipient out, and the transfer code the owner gave is what proves the handover; reason `TRANSFER_WITH_TRANSFER_CODE`) (32 random bytes, stored as SHA-256, single-use, 15 minutes, bound to the piece and to the scan event, which names the account; never on a staff scan). A code of another piece answers `409 TRANSFER_PRODUCT_MISMATCH`, naming no piece, so a seller who owns two pieces can no longer give the buyer of one the code of the other, keep the piece sold and later report it stolen (THREAT-MODEL X). The token is checked before the code is read (another piece, another account, another purpose: one `400 TRANSFER_TOKEN_INVALID`), so a scan of one piece cannot be used to learn which piece a code is for, and it is used up in the acceptance's transaction, so a refusal there leaves it unused. `TRANSFER_ACCEPT_REQUIRE_PRODUCT=false` makes both optional for an acceptance assisted by ORBES Client Services (§4: warned at every start in production); it acts on the API only, and no client of this release uses it (the verify app still asks for a signed-in scan, and the console offers no acceptance; a declared deviation of the plan), and while it is set the check is off for every pending transfer. Even then, an id that names no issued piece is refused only after the code has been read, with the answer the id of another piece gets, so the switch does not turn the acceptance into a way to enumerate the sequential product ids.
  - **Lock** (A-06, `POST /api/admin/owners/:id/lock`, ADMIN, audited `account.lock`): ORBES Client Services can lock an account, for example while a takeover is suspected. In one transaction the status becomes LOCKED, every session of the account ends, its pending transfers are cancelled, its open links to ownership certificates are withdrawn (F-06: a link shared by whoever took the account over stops showing the record, and stays withdrawn after an unlock), its entries in releases not drawn yet are withdrawn (P-R03: whoever took the account over cannot leave it in a draw), its open requests of the private salon are closed (P-X08: ORBES Client Services does not follow up a request made by whoever took the account over; the request reads the account's row `FOR SHARE`, so a lock under way wins and a request already on its way is closed with the others), its open entries in the LIVE RELEASES are removed (a piece it held going to the next in line) and its I'LL BE THERE withdrawn from the releases not opened yet and its **open recovery code is revoked**: a code obtained by fooling the identity check is precisely the takeover a lock is for (THREAT-MODEL U), so it must not work again after an unlock. A transfer request, a LOST / STOLEN declaration, a first registration (its claim code's check included) or the acceptance of a transfer already on its way is refused under the account's row lock (read again, as a share lock, before the piece is locked: no piece reaches a LOCKED account), and so are a password change and a sign-in whose password check was under way: login reads the account again `FOR NO KEY UPDATE` in the transaction that opens the session (an exclusive row lock, so concurrent sign-ins of one account, which may each reset the throttle, run in turn instead of deadlocking), so no session opened during the lock survives it to work again after an unlock, and a password change re-reads it before writing, so a password set during the lock cannot be used after the unlock. Sign-in then answers `403 ACCOUNT_LOCKED` only once the password is right (a wrong one answers as ever), so the lock reveals nothing to whoever does not hold it; the revoked code fails like a replaced one. The pieces stay registered. Unlocking (`account.unlock`) restores sign-in; cancelled transfers stay cancelled and the revoked code stays revoked (Client Services issues a new one if the customer needs it).
- **Admins:**
  - Lockout after 10 failures for 15 minutes, re-locking while the counter stays at the threshold, so guessing gets a bounded budget. **Trade-off (accepted):** anyone who knows an admin's email can keep that admin locked out by sending wrong passwords (slowed to 10 attempts per minute per IP by the `auth` rate limit). Mitigations: admin emails are not published, the console sits behind the same origin as the public app only if needed (an IP allow-list or VPN in front of `/admin` and `/api/admin` removes the exposure), and another ADMIN or `scripts/admin.ts` can act meanwhile; an ADMIN can also lift the lockout early from the Team page (*Unlock*, audited `admin.unlock`), after checking the `admin.login_failed` entries.
  - TOTP (RFC 6238); the secret is stored with AES-256-GCM. Required in production (`ADMIN_REQUIRE_MFA`, default true; `false` is accepted with a warning at every start). An ADMIN can reset a lost second factor (`POST /api/admin/admins/:id/totp/reset`, audited); the reset ends every session of that admin.
  - **First enrolment is trust on first use:** in the console, whoever first signs in with an admin's password can enrol their own authenticator. Recommended: enrol new admins from the shell (`scripts/admin.ts totp-setup` then `totp-enable`, which reads the secret from `ADMIN_TOTP_SECRET` as `create` reads the password, so it stays out of the shell history and the process list) and hand the secret over in person, before the password is used in the console.
  - Roles: ADMIN > OPERATOR > AUDITOR > RETAIL, where AUDITOR reads (customers' emails masked, §3.6) and RETAIL sells. A role does what the lower ones do, except the sale mode, which names its roles (RETAIL, OPERATOR, ADMIN): selling starts a warranty, so the read-only AUDITOR does not sell. **ADMIN only** (API §2.3): categories, revocation and retirement, reinstatement, code revocation, the revocation register, keys, console users, points of sale, a customer's recovery code, lock and export, the draw of a release (P-R03), a LIVE RELEASE ended now and an entry removed from it (`/api/admin/live/:id/end` and `/entries/:entryId/remove`, plan of 2026-10-04), and a model **discontinued or reinstated** (P-R06: `POST /api/admin/models/:id/discontinue` and `/reinstate`, server guard `minRole: 'ADMIN'`, console capability `discontinueModel`; the console asks for a typed phrase, `DISCONTINUE <SKU prefix>` or `REINSTATE <SKU prefix>`, because the change reaches what /verify says of every piece issued with the model; audited `model.discontinue` and `model.reinstate`, and reversible). Closing a request of the private salon is OPERATOR (P-X08, console capability `closeShopRequest`). LIVE RELEASE+ (plan of 2026-10-04): an AUDITOR reads the orders, the Atelier, the invoices, the segments and the Shopify exports, with every email and buyer masked; an OPERATOR moves an order through its steps, opens a return, enters its terms, buyer and piece, moves stock, sets a minimum, makes and issues the pieces to make and prints their work sheets, builds the segments and pastes the Shopify ids back; **ADMIN only**: the orders' alert delays, the stock locations and the carriers (`PUT /api/admin/orders/alerts`, the Settings' routes). Each is probed by `test/api/admin-roles.test.ts`.
  - **RETAIL, a seller's account (A-08, API §2.3, §16.17, §16.18):** ranked under AUDITOR, so the default rule of the guard (AUDITOR to read, OPERATOR to mutate) refuses it everywhere; only the routes that declare it let it through: the sale mode (`/api/admin/sale/lookup`, `/api/admin/sale/activate`, guarded by `roles: RETAIL, OPERATOR, ADMIN`), the list of points of sale (`GET /api/admin/retailers`, read only) and its own session, password and second factor. It can neither issue, nor download codes, artifacts or certificate cards, nor read products, scans, owners and their sheets, warranties, anomalies, the Cases queue, the analytics or the audit log (`test/api/admin-roles.test.ts` probes every route, those of the Cases queue, the owner's sheet, the analytics, batch issuance, print batches and the catalogue's edits included). A role this server does not know ranks 0 and is refused everywhere. The console gives it the sale shell and `#/sale` only; the server is the authority. OPERATOR and ADMIN may use the sale mode too; an AUDITOR, though ranked above RETAIL, may not (`403 FORBIDDEN`, no Sale mode link): it only reads.
    - **The sale is tied to a scan.** An activation needs a sale token: 32 random bytes, stored as SHA-256, single-use, 10 minutes, purpose `SALE_ACTIVATION` (a registration token is refused, and a sale token cannot register an owner), minted only when a staff scan of that very piece verified (steps 1–8 of the decision) and the piece can be sold (warranty neither started nor void, no client account holding it, not in a service), and usable only by the console user whose scan earned it. A seller can therefore start the warranty of a piece in front of them, not of any product id they know; a refusal rolls the use back. The activation checks again, under the piece's row lock, what the token was minted on: a client who registered the piece during the 10 minutes (`409 ALREADY_REGISTERED`), a service opened or the scanned code revoked meanwhile refuse it.
    - **A staff scan is recorded, not scored:** one ADMIN_TEST scan event naming the console user (`scan_events.admin_id`, only on ADMIN_TEST rows by a CHECK), outside every history rule (no history finding, no UNSOLD PIECE SCANNED, so a busy counter never makes a piece look suspicious); the console's verification events name the seller. The findings of steps 6–7 judge the code, not who scanned it, at the counter as on `/verify` (below): `VALID_SIGNATURE_UNREGISTERED`, `CODE_MISMATCH` and `GENOME_MISMATCH` are recorded with `staffScan: true`, so a forged but validly signed code shown at the counter still pages on a possible key compromise. The lookup draws from the `verify` rate budget, as `/api/v1/verify` does. The warranty activation is audited under the seller with the point of sale and the scan (`saleScanId`).
    - **A browser signed in to the console scans as staff (S-07, API §9.7):** `POST /api/v1/verify` reads the `orbes_admin` cookie (SameSite=Strict, so never on a cross-site request) and, when it is a session the console's guard would let in (alive, enabled, known role, no pending temporary password, second factor passed when required), records the scan as ADMIN_TEST under that console user, without the device, session or account pseudonyms, raises no UNSOLD PIECE SCANNED (stock checks do not drown the diversion signal, THREAT-MODEL W) and no history finding, and issues no registration token. The findings of steps 6–7 judge the code, not who scanned it: a staff scan still records `VALID_SIGNATURE_UNREGISTERED`, `CODE_MISMATCH` and `GENOME_MISMATCH` (details `staffScan: true`), so a forged but validly signed code that Client Services checks from a signed-in console browser still raises the CRITICAL key-compromise signal (§5 checklist, DEPLOYMENT §9.3). The state shown is the public one, scored on the public history only. Staff therefore scan and register a piece of their own from a browser that is not signed in to the console; a session the guard would refuse scans as the public.
    - Sellers' phones are shared counters: give each seller a nominative RETAIL account (never a shared one), enrol the second factor (required in production), and disable the account at the departure (one action, below).
  - **Staff accounts (the console's Team page, ADMIN only; API §17.7–§17.13):**
    - An ADMIN creates OPERATOR, AUDITOR and RETAIL accounts. The server draws a temporary password (16 Crockford base32 characters, 80 bits), returns it once and stores only its scrypt hash; it is never logged or audited. The account is flagged `password_change_required`: until it has chosen its own password, every admin route but logout, `me` and the password change answers `403 PASSWORD_CHANGE_REQUIRED`, the TOTP routes included, so the second factor is enrolled after the password is the staff member's own. Accepted: whoever holds the temporary password first owns the account, as with TOTP trust on first use; hand it over in person or over a trusted channel, and check the Team page shows TEMPORARY PASSWORD gone once the person has signed in.
    - **ADMIN is never granted from the console.** ADMIN accounts and the ADMIN role come from the shell (`scripts/admin.ts create --role ADMIN`, `role --role ADMIN`), where the second factor is enrolled out of band (above). The console can only step an ADMIN down to OPERATOR, AUDITOR or RETAIL.
    - **A departure is one action:** *Disable* sets `disabled_at` and deletes every session of the account in the same transaction; sign-in is then refused with the generic `INVALID_CREDENTIALS`, and a session that slipped through is refused and deleted at its next request. The account and its history stay (the audit log names it by id); *Enable* restores sign-in. Also: change a role (applies at the next request: the guard reads the role from the database every time), lift a lockout, list and end the sessions of an account.
    - **Guards:** an ADMIN cannot act on its own account (`409 SELF_ACTION`; resetting its own second factor and listing its own sessions excepted), and no change may leave the console without an active ADMIN (`409 LAST_ADMIN`, also enforced for the shell). Role changes and (de)activations are serialised by a transaction-scoped advisory lock (`ADMIN_ROSTER`), so two ADMINs disabling each other at once cannot both succeed.
    - Every change is audited with the acting ADMIN as actor: `admin.create`, `admin.role_change`, `admin.disable`, `admin.enable`, `admin.unlock`, `admin.sessions_revoke`, `admin.totp.disable`. The console's audit log names the acting console user, and the console user acted upon, by email, and the anomaly views name who triaged a finding; the emails are read at display time, the log itself keeps ids.
    - `scripts/admin.ts` has the same `role`, `disable` (`--yes`) and `enable` as a fallback when no ADMIN can sign in.
  - **Own password, every role (API §12.5):** the current password is re-checked; a wrong one answers `400 CURRENT_PASSWORD_INVALID` (a 401 would sign the console out) and counts as a failed sign-in towards the lockout, and a locked admin is refused before the password is looked at and again under the row lock before the new one is written (as at sign-in), so a stolen session cookie cannot be turned into a password-guessing oracle, not even by a burst of guesses in flight when the lockout fires. The new password follows the policy and must differ from the current one. The calling session is kept; every other session of the admin ends, and a sign-in with the old password whose check was under way when the change committed opens none either: the sign-in reads the password hash again under the admin's row lock before it opens the session, and writes a re-hash only if the hash is unchanged (as for customers, §3.3 above). When MFA is enforced, the change needs a session that passed the second factor once the admin has enrolled one (`403 MFA_REQUIRED`; before enrolment it stays open, for the temporary password): a session opened with the password alone, by someone who learnt it before the owner enrolled, cannot set a password only it knows and end the owner's sessions.
  - **Enrolling a second factor ends the admin's other sessions** (in the console and from the shell, audited `admin.totp.enable` with `sessionsRevoked`): they were opened with the password alone, and none is left alive for up to its 8 hours beside the new MFA-passed one.
- **Sessions:**
  - The token is 32 random bytes in an httpOnly, SameSite=Strict cookie, Secure in production. In production the cookies carry the `__Host-` prefix (`__Host-orbes_session`, `__Host-orbes_admin`, `__Host-orbes_device`): browsers then require Secure, `Path=/` and no `Domain`, so a sibling subdomain or a plain-HTTP response cannot plant or shadow them (session fixation, cookie tossing).
  - The database stores only the token's SHA-256 hash.
  - The token rotates on login **and on every privilege change**: TOTP enrolment replaces the session by a new MFA-passed one (new token and CSRF token, same absolute expiry), so a token captured before the step-up never carries MFA. Session lifetime is bounded (absolute expiry).
  - Each session has its own CSRF token.

### 3.4 Request integrity
- **Input validation:** strict zod schemas (unknown keys rejected), a 16 KB body limit, and length bounds on every string. The one exception to JSON is the console's photographs (F-04: `POST /api/admin/models/:id/image`, `POST /api/admin/products/:productId/photo`; P-R02: `POST /api/admin/models/:id/gallery`, a model's lookbook gallery; P-X01: `POST /api/admin/circle/posts/:id/photos`, a post of the owners' circle; the LIVE RELEASE: `POST /api/admin/live/:id/silhouette`, a release's silhouette; OPERATOR): the image itself, `image/jpeg` or `image/webp`, at most 1 MiB, a parser and a limit that exist on these routes only (any other type 415); its type is checked by its own bytes, never by its name, its dimensions bounded (4 096 px a side), an animated WebP refused, and its EXIF, XMP and every other metadata segment or chunk removed before it is stored, so no GPS position, camera settings, serial number or thumbnail reaches the public URL (`src/server/media/image.ts`). The colour profile (ICC) is the one block kept, whole, because the colours need it: its own text goes with it, which in a profile a device wrote names its maker and model. A photograph turned by its EXIF orientation is refused (the orientation goes with the EXIF, and the pixels are never turned). The edge of the VPS stack gives these upload paths 1 200 KB, every other request 64 KB. The verify route accepts any `code` string of at most 1024 characters, so that every undecodable submission is recorded as a `MALFORMED_CODE` scan (evidence for the console); the service reads only strings of 1–200 base64url characters that decode to exactly 79 bytes. Longer or non-string codes are refused with 400 and not recorded.
- **CSRF:** every cookie-authenticated mutation requires `x-csrf-token` equal to the session's token. The `Origin` must match the configured public origin (or `Sec-Fetch-Site: same-origin`); the session-less writes (account registration and login, the assisted account recovery `POST /api/v1/account/recover`, admin login, and a customer's report on a scan, `POST /api/v1/reports`) need that origin check alone.
- **Rate limits:** per IP and route group, covering verify, authentication, admin, claim attempts per product and transfer acceptance; the LIVE RELEASES' group `live` counts each network and, once the session is found, each account too (API §3).
- **Replay:** registration tokens, sale tokens (A-08), transfer tokens (F-03), transfer codes and recovery codes are random, stored hashed, single-use and time-limited, and consumed transactionally. A LIVE RELEASE's turn has its own secret (below, §3.6), bound to the entry and the turn's start, given to its account only, its SHA-256 alone stored, and worth nothing once the turn has passed. An ownership certificate's token (F-06) is a bearer link, not single-use: 32 random bytes, only their SHA-256 stored, valid 90 days at most, withdrawn by its owner at any time, and worth nothing once the piece changes hands or a loss or theft is reported (its validity is computed at each reading). Transfer codes (60 bits) are stored as HMAC-SHA256 under a server key derived with HKDF from `COOKIE_SECRET` (info `orbes/transfer-code/v1`): the lookup stays deterministic, but a leaked `ownership_transfers` table cannot be brute-forced offline. Rotating `COOKIE_SECRET` invalidates pending transfer codes.
- **SQL:** all queries go through Kysely's parameterised builder. Raw SQL is limited to migrations and static statements.

### 3.5 Response hygiene
- **Public responses:** never contain risk scores, thresholds, internal statuses, owner identities, retailer data, email addresses or stack traces. An ownership certificate (API §8.7) shows the record of one piece to whoever holds its link, and the same rule holds: no name, email, account or internal id, and no status beyond VALID or NO_LONGER_VALID (an unknown and a withdrawn link answer the same 404).
- **Errors:** a stable `{ error: { code, message } }` shape.
- **Claim codes:** returned once, at issuance. The certificate card endpoint (`POST /api/admin/certificates`, OPERATOR) takes a code back only to print it: it checks the code against its scrypt hash first, and never stores, logs, audits or repeats it in an error (audit entries carry product ids). The card draws the code as paths, never as text, and every file is a `no-store` attachment. The card 79t prints the claim code in plain sight beside the piece's ORBES CODE, with no scratch-off panel (the owner's choice, 2026-10-07, accepted), so whoever holds the card before the first registration can register the piece. A batch (`POST /api/admin/products/batch`, API §14.11) returns each piece's code once, in its result (`no-store`), and audits product ids only; the console keeps a batch's codes in the page's memory, never in browser storage, and until the certificate cards or the results file are saved or the codes hidden, it asks before the page is left (closing the tab, another view, sign-out). A session that ends meanwhile (its absolute 8 h, a revocation) does not take the page with it: the console says the session has ended and keeps the page, its codes included, so the results file (made in the browser, no request) can still be saved; the sign-in comes once the page is left, through the same question. A batch whose session ends between two of its requests shows the pieces already signed, with their codes. The Anomalies badge's refresh, which runs on a timer, never ends a session or replaces a page: a 401 only stops it. The results file holds the codes: it is to be kept as the cards are.
- **Security headers:**
  - CSP: `default-src 'self'; script-src 'self'; style-src 'self'; img-src 'self' data: blob:; connect-src 'self'; worker-src 'self' blob:; media-src 'self' blob:; frame-ancestors 'none'; base-uri 'none'; form-action 'self'`
  - `Permissions-Policy: camera=(self)`
  - `Referrer-Policy: no-referrer`
  - HSTS in production
  - `X-Powered-By` removed

### 3.6 Privacy
- Device identifiers are random cookies. Only `HMAC(pepper, id)` is stored.
- IP addresses are never stored. Only `HMAC(pepper, ip)` is kept, for rate limiting and diversity counting.
- Geography is coarse: a country, plus lat/lon rounded to 0.1°, when the trusted edge provides them (`GEO_MODE=cloudflare` or `headers`) or, with `GEO_MODE=mmdb`, from a local GeoIP database lookup of the client IP on the server (`src/server/geo/mmdb.ts`; the IP is looked up in memory and never stored, and no region is derived).
- Codes contain no personal data.
- **Customers' reports on their scans** (`POST /api/v1/reports`, C-02): on a result that was not authentic, the customer may say where they saw or bought the piece, with a place (≤ 200 characters) and a note (≤ 500). That free text is **personal data** (it may name a seller, a place, a person). It is kept exactly as long as the scan it is attached to, and deleted with it; it is shown to an admin session only (the Cases queue, the scans and anomalies lists), never in a public response, and never copied into the audit log, which is permanent: `scan.report` and `scan.report.close` name the scan alone, and the case's resolution note stays with the case for the same reason. The verify app asks the customer to leave out their name and contact details. One report per scan, within 24 hours of a non-authentic result, rate group `verify` (DATABASE §5.22, API §8.5).

The console reads the entrants' emails, masked for an AUDITOR (the board and its stream, the entries, the reservations and their CSV, the bot radar, the collector insights). A lock of the account removes its open entries and withdraws its interest in releases not opened yet; the right of access exports every entry, its add-ons and its interest. The privacy policy says so (`legal.content.test.ts`, TERMS-FACTS R114, R115, R117).
  - **PAY takes no payment** (choices 4 and 33): it confirms a reservation that ORBES Client Services concludes outside the service; no payment library, no payment route (TERMS-FACTS N8).
  - **Rate limits.** The group `live` counts each network (10 × the `api` budget, for the collectors of a boutique who share its wifi and poll their room every 2 s while a stream is lost) and each signed-in account (the `api` budget), so one account cannot spend its network's budget alone. Every mutation needs the session's CSRF token and the same-origin rule; the board's POSTs the same-origin rule.

ADMIN: END NOW after a typed phrase, REMOVE. Every route has its role probe (`test/api/admin-roles.test.ts`).
- **The orders and the collectors of LIVE RELEASE+** (plan of 2026-10-04; `services/orders.ts`, `fulfilment.ts`, `atelier.ts`, `stock.ts`, `invoices.ts`, `journal.ts`, `after-room.ts`, `participation.ts`, `segments.ts`, `question.ts`, `activity.ts`, `shopify.ts`; API §10.13 to §10.16, §16.24 to §16.27; DATABASE §5.46 to §5.61):

An AUDITOR reads them masked (`J*** D***`, `***`) on the board, an order's page, the CSV, the Invoices page, its CSV and its PDFs, the Shopify order export and the client sheet, which never shows them at all.

The journal is for future connections and has none: the server sends no request out (TERMS-FACTS N10), and the Shopify exports are files the console downloads.

The account's export carries its orders (with the buyer's details, each step and its note, the carrier and the tracking number, the invoices), its answers and its places in an after-room.
- **Customers' accounts in the console** (A-06, `routes/admin/owners.ts`, `services/owners.ts`):
  - **Masked for an AUDITOR.** A customer's email is personal data an auditor does not need: the server sends it to an AUDITOR as `j***@example.com` (the first character, then the domain) in the owners list, its searches, the owner's sheet and a product's ownership history, the entries of a release (P-R03), the answers to a circle invitation (P-X01), the requests of the private salon (P-X08), the LIVE RELEASES' board, entries, reservations, bot radar and collector insights, and LIVE RELEASE+'s orders, invoices, segments' members and Shopify order export (with the buyer's name and address); OPERATOR and ADMIN read it in clear. Search terms travel in the query string, which neither the app's log nor Caddy's access log keeps.

It leaves out what cannot be given back readably, and says so: password and code hashes, the hashes of the certificate links' tokens, IP and device pseudonyms. The audit log has no index on the actor, so an export reads the whole log once: accepted for a rare ADMIN request.
  - **Identity check.** A recovery code, a lock at the customer's request and an export are given only after ORBES Client Services has checked that the caller is the account holder. The procedure is written with counsel; the [sales playbook](launch/SALES-PLAYBOOK.md) (J-09), §6, outlines it for staff: the client gives the facts and staff compare them with the console, nothing is read out first, and the code is read to the person checked, never sent or written down. After the account's exact email, nothing a scan shows counts as proof: the piece's identity and model, its warranty's start date and the REF of a scan are shown to anyone who scans its code or a copy of it (a REF's Reference names the owner whoever scans), so they prove at most access to the piece or to a photograph of its code, and a scan made during the call is only an extra check that the piece is at hand. Two facts no scan reveals are required: the invoice of a piece the account registered itself (FIRST REGISTRATION) **and still holds** (its Pieces row `Until` = CURRENT), its point of sale and date together against the warranty's Purchase (for a piece received by transfer the original invoice proves nothing, and neither does the invoice of a piece the account has since transferred away: a seller commonly hands the invoice to the buyer, who would then know it and, for an account with no other piece, the rest too), and what the client says of the account (its other pieces and since when, its recent transfers) against the owner's sheet; in a boutique, an ID document in the name on the invoice as well. An account whose piece is LOST or STOLEN always needs the invoice, and a STOLEN is lifted only in a boutique, with the piece, the invoice and an ID document; without these facts, or in doubt, no code is given and the case goes to counsel. Until it is final, the audit trail (who issued, locked or exported, and when) is the control.
- Retention: with `SCAN_RETENTION_DAYS` set, housekeeping deletes scan events older than the period, with their authentication events, scan tokens and customers' reports (DATABASE §10). The period is a legal decision; it cannot be shorter than the anomaly look-back (30 days by default), and production warns at every start while it is unset (scan history is then kept indefinitely).
- Daily statistics: before any purge, housekeeping counts every complete UTC day into `scan_daily_stats` (day, country, verification state, event type and a count; DATABASE §5.24). The table holds nothing about a scan: no pseudonym, code, piece, account or coordinate, and staff scans are not counted. It is what the console's Analytics view reads (AUDITOR, API §16.16), so a short retention period keeps the trends.

### 3.7 Audit and integrity monitoring

### 3.8 Anomaly detection
- The rules are pure functions over scan history. Thresholds are configuration and are never exposed.
- The system never revokes automatically. A human reviews anomalies.
- **Triage in the console** (API §16.4, §16.14, §16.15): the ANOMALIES link and the tab title carry the count of OPEN HIGH and CRITICAL findings, refreshed every minute while a console tab is visible; the list is ordered most severe first; a finding's detail shows its product's scans in its window (countries, distinct devices, the scan that raised it), pseudonyms only. Its decision dialog can mark the piece COUNTERFEIT FLAGGED or STOLEN (OPERATOR) and revoke its code (ADMIN, typed phrase) before resolving it: only on the admin's tick, through the same routes and role checks as the product page, each step audited with a reason that cites the finding.
- A logged-in current owner keeps `AUTHENTIC_OWNERSHIP_VERIFIED`, with an `UNUSUAL_ACTIVITY` notice. This limits the damage of anomaly poisoning.
- **Before first registration**, anomaly poisoning cannot lock out the buyer either: when a scan is `SUSPICIOUS_ACTIVITY` only because of the risk score, the product has no owner, is open for registration and ships with a claim code, the response still carries a registration token with `claimCodeRequired: true`. The token is useless without the claim code from the certificate card; products without a claim code get no token while suspicious. The verification app offers it on the UNUSUAL ACTIVITY result itself, under the help line, as **DO YOU HOLD THE CERTIFICATE CARD?** (sign-in, then the claim code, required), without showing any product data (`genome/src/web/verify/view-model.ts`, `ownershipMode`). Residual risk: the claim-code limit (5 failures per product per rolling hour) counts every account's failures and then refuses the right code too, so poisoning plus 5 wrong claim codes an hour can still hold the buyer's registration back; the app then says that registration is held for up to an hour and that ORBES Client Services can assist them (THREAT-MODEL E). Counting failures per account or per source as well is server work still to do. The section also shows a visitor that the piece is unregistered and open for registration, an accepted disclosure (BRAND §4.1).
- **Sources, not cookies (SEC-7):** scan velocity and diversity count distinct sources — the IP pseudonym, else the device-cookie pseudonym, else the session — because device cookies are client-controlled: a client that drops its cookie on every request would otherwise look like many devices. Accepted trade-off: many phones behind one address (a boutique wifi, a carrier NAT) count once. Travel and dispersion use the coarse geography.
- Weights and thresholds are internal (PLATFORM-CONTRACTS §2.5). A same-place burst (scan velocity 45 ⊕ source diversity 30 = 62) reaches the default threshold of 60 without a geographic signal.

## 4. Configuration hardening (production)

`loadConfig` refuses to start in production when any of these hold:
- the database is PGlite;
- the key provider is `memory`;
- `COOKIE_SECRET` or `IP_HASH_PEPPER` is shorter than 32 characters, still the development default, or has too little variety; or both are the same secret;
- `PUBLIC_ORIGIN` is not `https:`;
- the local key provider has no `KEY_ENCRYPTION_KEY`, or it is degenerate (all bytes identical);
- `TRUST_PROXY=true`: Fastify would take the left-most `X-Forwarded-For` entry as the client IP, and that entry is written by the client, so rate limits (logins, claim and transfer codes) and IP pseudonyms become forgeable. List the proxy addresses or ranges instead;
- `TRUST_PROXY` is a number (a hop count such as `1`): ambiguous, and Fastify's handling of numbers trusts nothing or everything depending on the version. Also refused outside production;
- `GEO_MODE=cloudflare` or `GEO_MODE=headers` without `TRUST_PROXY`: the location headers would be accepted from any client (and, behind Cloudflare, every client would share the edge's IP for rate limiting);
- `GEO_MODE=mmdb` without `TRUST_PROXY`: production always sits behind a TLS proxy, so the client IP would be the proxy's own address and every lookup would silently find nothing.

Refused in every environment: `GEO_MODE=mmdb` without an absolute `GEO_MMDB_PATH` (a missing file at that path is not an error: location is then simply unknown).

Accepted with a warning at every start (`configWarnings`): `ADMIN_REQUIRE_MFA=false` in production, `TRANSFER_ACCEPT_REQUIRE_PRODUCT=false` in production (a transfer code accepted without a scan of its piece, F-03: API level only, for an acceptance assisted by ORBES Client Services, not as a steady state), and no `SCAN_RETENTION_DAYS` in production.

`npm start -- --demo` (demo mode) is refused in production and with any `DATABASE_URL` other than `pglite:memory`.

## 5. Operational security checklist

- [ ] Signing keys in a KMS/HSM (or LocalKeyProvider on a dedicated host with encrypted disk).
- [ ] `KEY_ENCRYPTION_KEY`, `COOKIE_SECRET` and `IP_HASH_PEPPER` stored in a secret manager and rotated on staff changes.
- [ ] TLS everywhere. HSTS preload once the domain is stable.
- [ ] Database: least-privilege app role, TLS, encrypted backups, point-in-time recovery.
- [ ] Periodic `audit/verify`, with the chain head exported to WORM storage.
- [ ] Alerting on CRITICAL anomalies (`VALID_SIGNATURE_UNREGISTERED`, `CODE_MISMATCH`), which indicate key compromise. The console's badge reaches only someone who has the console open; an alert outside it (DEPLOYMENT §9.3) is still to set up.
- [ ] Admin accounts with TOTP. AUDITOR role for analysts.
- [ ] A written identity check for customers, applied by ORBES Client Services before an ADMIN issues a recovery code, locks an account at the customer's request or exports it (§3.6; to finalise with counsel, outlined for staff in the [sales playbook](launch/SALES-PLAYBOOK.md), §6); recovery codes are read to the customer, never stored or forwarded.
- [ ] One named account per person, created on the Team page (OPERATOR, AUDITOR, RETAIL) or from the shell (ADMIN); never a shared login, a seller's phone at a shared counter included (one RETAIL account per seller, §3.3). Two active ADMINs at least, so that one can act when the other is away.
- [ ] Departures: disable the account on the Team page the same day (its sessions end at once), and rotate the secrets it could have seen (above).
- [ ] Quarterly: review the Team page (roles, accounts still marked TEMPORARY PASSWORD, locked or disabled accounts) and the `admin.*` entries of the audit log.
- [ ] Key rotation at least yearly. A revocation drill documented and rehearsed.
- [ ] `npm audit` and dependency updates in CI.
