# ORBES GENOME CODE™ — Threat Model

Status: v0.1 · Scope: ORBES CODE-01 / GENOME-01, the verification service, the admin console and the key custody chain.

This document explains what each part of the system protects and what it cannot protect. It hides no limitations. Two rules shape everything below:

1. **A static printed code can be copied.** Scanning an ORBES CODE proves that ORBES issued and signed that code. On its own it never proves that the physical object in your hand is the original.
2. **Security never depends on secrecy of the algorithm.** We assume attackers know the full source code, the code format, the Genome permutation, the public keys, every network request and every public API.

---

## 1. Assets

| Asset | Why it matters |
|---|---|
| Ed25519 signing keys | Whoever holds a private key can issue codes that verify as ORBES. |
| Product registry (products, genomes, codes) | It is the ground truth that turns a valid signature into a *registered product*. |
| Lifecycle, ownership and warranty records | They decide the customer-facing state and the transfer of ownership. |
| Scan history | It is the input to clone and duplication detection. It also holds personal data (pseudonymous) that must be minimised. |
| Admin accounts | They can issue, revoke and reinstate products and rotate keys. |
| Customer accounts | They hold ownership rights over products. |
| Brand trust in the verification UX | A verification page shown by the wrong party, or one that overstates, damages trust. |

## 2. Adversaries

- **Counterfeiter (casual):** copies a code from a photo, a listing or a boutique display.
- **Counterfeiter (industrial):** mass-produces goods and has access to genuine products, printing equipment and photography.
- **Grey-market reseller:** tries to make stolen or diverted goods look clean (pieces diverted before their sale: THREAT W).
- **Online attacker:** scripts the public API, attempts brute force and replays requests.
- **Phisher:** operates a look-alike verification website.
- **Insider:** an operator with admin access, or a contractor with infrastructure access.
- **Malicious seller:** a boutique employee with a RETAIL account (A-08), whose sale mode starts warranties (THREAT V).
- **Infrastructure attacker:** has compromised the database, a backup or a host.

## 3. Trust boundaries

```
 [ physical artifact ] --camera--> [ customer browser ] --TLS--> [ verification service ] --> [ PostgreSQL ]
                                         ^ untrusted                     |  trusted            ^ trusted (integrity monitored)
                                                                           +--> [ KeyProvider: local file | KMS | HSM ]
 [ admin browser ] --TLS + session + CSRF + role + (TOTP)--> [ admin API ]
```

Nothing the browser computes is trusted. The decoder runs client-side only for speed. The server re-parses every byte, re-checks the CRC, verifies the signature, consults the registry and makes every decision.

## 4. Threats

### THREAT A — Screenshot of a legitimate ORBES Code

| | |
|---|---|
| **Attack** | Photograph or screenshot a genuine code, for example from a resale listing, and present it, printed or on a screen, as proof of authenticity. |
| **Current protection** | (1) The verification state never claims physical authenticity. It reports a signed, registered identity and its lifecycle. (2) Every scan is recorded with device, coarse location and time, and the anomaly engine scores impossible travel, velocity, device diversity and geographic dispersion. (3) Ownership: when the product is registered, non-owners see **AUTHENTIC — REGISTERED** ("this identity belongs to a registered owner"). A buyer can therefore ask the seller to perform an in-app transfer, which only the real account holder can do. (4) First registration needs a fresh single-use scan token (15 min). When ORBES prints a claim code under the scratch panel of the certificate card, it also needs that code. A screenshot alone therefore cannot claim an unregistered product. |
| **Residual risk** | **High for unregistered products with no claim code.** A screenshot is indistinguishable from the original at the data level. A single re-use of a screenshot elsewhere may never trigger an anomaly. |
| **Future mitigation** | Secure NFC / secure element challenge-response (see [FUTURE-HARDWARE](FUTURE-HARDWARE.md)). Screen-capture detection heuristics (moiré, refresh banding). Customer education: "ask for a transfer". |

### THREAT B — Copying the printed code onto counterfeit products

| | |
|---|---|
| **Attack** | Reprint a genuine code on counterfeit goods. |
| **Current protection** | The same detection as in A, aggregated over many products. Each physical copy produces scans from distinct sources (addresses) and places. `DEVICE_DIVERSITY`, `SCAN_VELOCITY`, `GEO_DISPERSION` and `IMPOSSIBLE_TRAVEL` raise the risk score (a burst of many sources in one place is enough on its own), and the customer then sees **UNUSUAL ACTIVITY DETECTED**. Admins can revoke the code and re-issue a new one (issue + 1) for the genuine owner's product. The genuine owner, recognised through their account, keeps **OWNERSHIP VERIFIED**. |
| **Residual risk** | **Medium.** Low-volume copying (a handful of pieces) can stay below thresholds. Detection is statistical and always after the fact. |
| **Future mitigation** | Hardware binding. Physically unclonable features (micro-engraving, tamper-evident substrates) referenced in a future CODE version. Retailer-side activation that binds code and sale: started with the sale mode (A-08), where a seller's phone scans the piece and starts its warranty only through a token of that scan (THREAT V); a copy of an activated code then meets AUTHENTIC — REGISTERED or FIRST REGISTRATION with a claim code the counterfeiter does not hold. |

### THREAT C — Altering the product ID

| | |
|---|---|
| **Attack** | Edit the identity bits in a genuine code, for example to impersonate a more valuable model, or forge a code for an arbitrary ID. |
| **Current protection** | The Ed25519 signature covers the whole canonical payload (`ORBES-CODE/v1 ‖ 0x00 ‖ payload`): version, key id, identity, issue, date and nonce. Any modified bit fails verification and gives **INVALID SIGNATURE**. The Genome is derived from the signed identity, so a printed Genome that no longer matches gives **UNUSUAL ACTIVITY** (`GENOME_MISMATCH`). |
| **Residual risk** | **Negligible.** It would require breaking Ed25519 (≈ 2¹²⁸ work). |
| **Future mitigation** | None needed. Migrate to a post-quantum signature in a future CODE version when standardised options fit the print budget. |

### THREAT D — Creating random fake codes

| | |
|---|---|
| **Attack** | Generate syntactically valid ORBES CODEs with random content, or with a well-formed payload and a random signature. |
| **Current protection** | Signature verification with a key looked up by `key_id`. Unknown key ids give **INVALID SIGNATURE**. Random data passing the RS/CRC framing still fails the signature. The decoder may happily read a forged artifact: correctly decoding a forgery is expected, and rejection happens at verification. |
| **Residual risk** | **Negligible.** |
| **Future mitigation** | — |

### THREAT E — Replay attacks

| | |
|---|---|
| **Attack** | (1) Replay a captured verification request. (2) Replay a registration token or transfer code. (3) Replay many scans of someone else's product to make it look suspicious ("anomaly poisoning"). |
| **Current protection** | (1) Verification is an idempotent read. Replaying it reveals nothing new and is rate-limited per IP and route. (2) Registration tokens, transfer tokens (F-03) and transfer codes are random, stored hashed, single-use and short-lived, and are consumed in the same transaction as the ownership change; a transfer token is bound to its piece and to the account whose scan earned it, so one replayed by anyone else is refused (THREAT X). (3) The anomaly engine never revokes automatically. A logged-in owner always sees **OWNERSHIP VERIFIED** (with a notice), not "suspicious". Anomalies are reviewed by people. Device and IP data are pseudonymous HMACs, which still lets rate limits and diversity counts tell sources apart. Velocity and diversity count distinct **sources** (the IP pseudonym, else the device cookie, else the session), so one machine that drops its cookie on every request is one source and cannot inflate the count on its own; poisoning needs many addresses. When an unregistered product shipped with a claim code is suspicious **only** because of its scan history, the response still carries a registration token (`claimCodeRequired: true`), and the verification app offers it under **DO YOU HOLD THE CERTIFICATE CARD?**, so the buyer holding the certificate claim code can register despite the poisoning. |
| **Residual risk** | **Low–medium.** An attacker with many addresses can make an unregistered product show **UNUSUAL ACTIVITY** to non-owners. That is a nuisance attack, not an authenticity break; products issued without a claim code cannot be registered while it lasts. Accepted trade-off of source counting: many genuine phones behind one address (a boutique wifi, a carrier NAT) count once. **Registration can still be held back:** the claim-code limit (5 failures per product per rolling hour, K) counts failures from every account and refuses the right code too while it holds, and a failed attempt does not spend the scan's token. An attacker who poisons the history (each scan of a copy gives them a registration token, as the buyer's own scan does) and sends 5 wrong claim codes an hour from a free account keeps the buyer from registering for as long as they keep it up. The app tells the buyer that registration is held for up to an hour and that ORBES Client Services can assist them; Client Services can examine the piece, and an admin can revoke the copied code and re-issue the piece (THREAT B). Fixing the cause is server work still to do: count failures per account or per source as well, and check the code before the product's counter so that other accounts' failures do not block the right code. **Accepted disclosure:** the certificate-card section shows only when the history alone made the scan unusual and the piece is unregistered, open for registration and has a claim code, so a visitor can tell that case from a piece reported stolen or already registered (BRAND §4.1). The `registration` field of the response already said so (API §9.2). |
| **Future mitigation** | Proof-of-possession for scans (hardware challenge). Bot detection on the verify endpoint. Weighting scans by device reputation. |

### THREAT F — Database compromise

| | |
|---|---|
| **Attack** | Read or modify the database: alter statuses, add fake products, change ownership, erase scan history. |
| **Current protection** | No private keys in the database (only public keys and provider references). IP addresses and device ids are stored as HMACs with a pepper held outside the DB. The audit log is **hash-chained** and append-only (a trigger rejects UPDATE/DELETE), so tampering becomes detectable with `verifyChain()`. `product_status_history` is append-only too, and `genomes` and `cryptographic_keys` rows cannot be deleted (no key id can be reused for a different key); these triggers stop application bugs and a compromised application role, not a database owner. Codes remain *self-verifying*: an attacker who inserts a fake product row still cannot produce a valid signature for it. Passwords, claim codes and TOTP secrets are scrypt-hashed or AES-GCM encrypted. |
| **Residual risk** | **Medium.** A write-capable attacker can change lifecycle and ownership state (for example un-revoke a product). The hash chain detects but does not prevent this, and an attacker with full DB control could rewrite the whole chain. |
| **Future mitigation** | Periodically anchor the audit-chain head outside the DB (signed by a separate key, published or stored in WORM storage). Postgres row-level security and least-privilege roles (app vs migrations vs read-only analytics). Point-in-time recovery. Integrity monitoring. |

### THREAT G — Private key compromise

| | |
|---|---|
| **Attack** | Steal a signing key and mint codes that verify as ORBES. |
| **Current protection** | The `KeyProvider` abstraction lets production keys live in a KMS or HSM, where they are non-exportable and signing goes through IAM. The local provider encrypts keys at rest with AES-256-GCM, with file mode 0600 and a dedicated encryption key from the environment. Every code names its `key_id`. Keys can be **revoked with a compromise timestamp**: codes whose registry record predates the compromise remain valid, and anything else signed by that key — later codes and identities ORBES never registered alike — gives **INVALID SIGNATURE** (the revoked-key rule runs before the registry lookup). The public key list publishes `revokedAt` and `compromisedAt`, so offline verifiers can refuse codes dated after the cut-off. Even before revocation, forged codes for *existing* products fail the registry nonce/payload-hash match (`CODE_MISMATCH`, CRITICAL, shown as **UNUSUAL ACTIVITY**), and forged codes for *unregistered* identities give **UNKNOWN** plus a CRITICAL `VALID_SIGNATURE_UNREGISTERED` anomaly. That anomaly is an early compromise alarm, raised by every scan, including a staff scan from a browser signed in to the console (S-07: Client Services checking a suspicious piece a customer brought in; details `staffScan: true`, API §9.7). Rotation is a single admin action, and verify-after-sign guards against faulty signer output. |
| **Residual risk** | **Medium until detection.** Between theft and revocation an attacker can mint codes for unregistered identities. Those show UNKNOWN, not AUTHENTIC, so customer-facing damage is limited. |
| **Future mitigation** | HSM with dual control. Short-lived signing keys per production batch. Transparency log of issued codes. Offline root key that certifies operational keys. |

### THREAT H — Malicious frontend modification

| | |
|---|---|
| **Attack** | Tamper with the verification web app (XSS, a malicious extension, a compromised CDN) or modify the client to report AUTHENTIC. |
| **Current protection** | The client holds no secrets. The server decides every state. Strict CSP (`script-src 'self'`, no inline script or style, `frame-ancestors 'none'`). Assets are self-hosted with no third-party scripts. A modified client can only lie *to its own user*. It cannot make the server record or issue anything it would not otherwise accept. |
| **Residual risk** | **Low–medium.** A user on a compromised device can be shown anything. |
| **Future mitigation** | Subresource integrity for any future external asset. A signed verification receipt (server-signed result with a short code) that a second device or ORBES client services can check. |

### THREAT I — Fake ORBES verification website

| | |
|---|---|
| **Attack** | A counterfeiter prints a QR code or link that leads to a look-alike site which always says AUTHENTIC. |
| **Current protection** | The ORBES CODE is not a URL and does not open a website by itself. The customer must go to the official ORBES domain, so packaging and the website consistently say: "verify only at theorbes.com/verify" (wording in the [packaging kit](launch/PACKAGING-KIT.md)). The public key set is published at `/.well-known/orbes-keys.json`, so third parties (resellers, insurers) can verify signatures independently. Account-based ownership means a fake site cannot show the customer's own registered products. An ownership certificate (F-06, THREAT Y) is read only on the official domain (`/verify/c#…`); its PDF letters that address and carries it as a link, and says to check it there live, so a forged or edited PDF is caught by the reading it asks for. |
| **Residual risk** | **Medium.** Phishing cannot be eliminated technically. |
| **Future mitigation** | A native app with pinned keys. Verification receipts (the ownership certificate, F-06, covers the record of a piece shared by its owner, not the result of a scan). Domain monitoring and takedown. Customer education. |

### THREAT J — Mass-produced counterfeits using one legitimate identity

| | |
|---|---|
| **Attack** | Buy one genuine product and reprint its code on thousands of fakes. |
| **Current protection** | This is the strongest case for statistical detection. Hundreds of devices across many countries quickly exceed the `DEVICE_DIVERSITY`, `GEO_DISPERSION`, `SCAN_VELOCITY` and `IMPOSSIBLE_TRAVEL` limits, and the identity is flagged for non-owners. ORBES can revoke the code (every copy then reads **REVOKED**) and re-issue a new code to the genuine owner. Re-issue increments the issue number and creates a fresh nonce. |
| **Residual risk** | **Medium.** Detection lags the first sales. Customers who never scan are not protected. |
| **Future mitigation** | Hardware binding for high-value lines (policy `PRINTED_CODE+SECURE_NFC`). Retail activation that binds sale to code (the sale mode, A-08, binds the warranty start to a staff scan of the piece; binding the code itself to one sale needs hardware). Marketplace monitoring using the public verification API. |

## 5. Additional threats considered

| Threat | Protection | Residual |
|---|---|---|
| **K. Brute force of claim codes or transfer codes** | 12 Crockford-base32 characters (60 bits). Claim codes are stored as scrypt hashes; transfer codes as HMAC-SHA-256 under a server key derived from `COOKIE_SECRET`, so a leaked database cannot be brute-forced offline. Per-product attempt limits (5/hour, across all accounts; while the limit holds, the right claim code is refused too, which an attacker can use to hold a piece's registration back, THREAT E). Route rate limits. The certificate card endpoint also checks typed claim codes against their hashes, but only for an OPERATOR session (TOTP in production), with every refusal audited (`certificate.render_refused`); its checks stop at the first wrong code, and each admin has one certificate request in progress at most (API §15.7). Batch issuance (API §14.11) hashes one new claim code per piece, one piece after the other, and each admin has one batch in progress at most. | Negligible. The certificate endpoint's cost is an availability matter, not a brute-force one: a request of 50 correct codes still runs 50 scrypt checks one after the other, so an OPERATOR session (an insider, with TOTP) can keep one of the server's few scrypt threads busy and slow other users' logins and registrations a little while it does; it cannot run two at once, and every request is audited. |
| **L. Admin account takeover / insider abuse** | scrypt passwords, lockout, TOTP required in production (`ADMIN_REQUIRE_MFA`), a new session token on the MFA step-up, `__Host-` cookies in production, roles (AUDITOR reads, RETAIL only sells, THREAT V), CSRF and SameSite=Strict cookies, every mutation audited with a hash chain. Key revocation, reinstatement, retirement and TOTP resets are ADMIN-only. The catalogue's public words (a model's name, care instructions and collection, a collection's name: read live by every result of their pieces) are an OPERATOR's to edit, each change audited with the values before and after and the number of issued pieces it reached (`model.update`, `collection.update`); a model's category and SKU prefix never change, below the service too (trigger). Staff accounts (Team page, ADMIN only): one named account per person; a departing member is disabled in one action that also ends every open session; the console never grants ADMIN (shell only, with an out-of-band second factor), an ADMIN cannot act on its own account and the last active ADMIN cannot be removed; a temporary password opens nothing but the change to the member's own. A stolen admin session cannot guess the password through the password change: a wrong current password counts towards the lockout, and a locked admin is refused first and again under the row lock before the new password is written, so guesses in flight when the lockout fires change nothing. | Medium for insiders with ADMIN role. Mitigate with dual control (future). First TOTP enrolment in the console is trust on first use (enrol from the shell instead, SECURITY-MODEL §3.3), and so is a temporary password: whoever holds it first owns the account (hand it over in person); the lockout can be abused to keep a known admin out (accepted, SECURITY-MODEL §3.3). An ADMIN can demote or disable the other ADMINs (never the last one): with two ADMINs, one rogue ADMIN can lock the other out of ADMIN rights until the shell restores them. |
| **M. Malicious images against the decoder** (DoS or crash) | The decoder is memory-bounded, never throws (fuzz-tested) and runs in a Web Worker client-side. The server never decodes customer images. | Low. |
| **N. Supply-chain compromise of dependencies** | A small, well-known dependency set, a lockfile, and `npm audit` in CI. Core cryptography uses `node:crypto` (server) and audited noble libraries. | Medium (industry-wide). |
| **O. Privacy harm from scan tracking** | No raw IPs. HMAC device and IP identifiers. Coordinates rounded to about 10 km, taken only from trusted edge headers (`GEO_MODE=cloudflare` or `headers`, behind `TRUST_PROXY`) or from a local GeoIP lookup of the client IP on the server (`GEO_MODE=mmdb`; the IP is looked up in memory and never stored). No personal data in codes. Public responses never reveal owner identity. Optional retention limit: `SCAN_RETENTION_DAYS` purges scan events with their authentication events, scan tokens and customers' reports (DATABASE §10), after housekeeping has counted every complete day into the anonymous `scan_daily_stats` (day, country, state, type, count: nothing that identifies a scan, a device or a person), so the trends do not argue for a long retention. A customer's report (where they saw or bought a piece) is free text kept only as long as its scan, never copied into the permanent audit log, and the app asks for no contact details (SECURITY-MODEL §3.6). | Low. The retention period is a legal decision to take with counsel; while `SCAN_RETENTION_DAYS` is unset, scan history is kept indefinitely and production warns at every start. |
| **P. Misleading claims** | Copy deck reviewed: no "real", "100% genuine" or "impossible to counterfeit" wording. States describe exactly what was verified. | Low. |
| **Q. False INVALID SIGNATURE on a genuine piece** (a worn or glared code miscorrected by Reed-Solomon into a CRC-valid but wrong word) | The decoder never erases more than 70 bytes, so at least 15 parity bytes still check every correction (0 miscorrections in 100 000 random words at 70, against 18 at 80), then CRC-16. The verify app submits a read whose correction load 2·errors + erasures exceeds 50 only after a second, independent frame decodes to identical data (ORBES-CODE-SPEC §11). | Very low. A wrong verdict on a genuine piece is answered by rescanning, and every result invites Client Services. |
| **R. Credential stuffing against customer accounts** | Per-IP `auth` rate limit plus a per-account throttle (10 wrong passwords in 15 minutes) that answers exactly like a wrong password; a wrong current password of a password change (`POST /api/v1/account/password`) counts in the same throttle and answers 400, so a stolen session guesses no faster. scrypt slows every attempt. | Low. `EMAIL_TAKEN` on registration still reveals that an email has an account (accepted until an email channel exists). |
| **S. Edited code-version nibble** (a forged or copied frame relabelled as a newer code version, CRC recomputed) | A frame naming a version without a profile on the server is answered UNKNOWN (`UNSUPPORTED_CODE_VERSION`), never an authentic state, recorded and logged as a server warning (ORBES-CODE-SPEC §12). The camera decoder does not read such a code at all (FORMAT, unsupported code version). | Low. The attacker trades INVALID SIGNATURE for UNKNOWN ORBES CODE, which also tells the customer the code is not confirmed; repeated warnings point at probing. |
| **T. False or abusive reports on scans** (`POST /api/v1/reports`: flooding the Cases queue, sending staff after an innocent seller, or free text used to carry abuse) | A report needs a customer's scan (a staff scan from a browser signed in to the console takes none) that was **not authentic**, less than 24 hours old and not yet reported: one report per scan, so each one costs a verification first, and both draw on the `verify` rate budget. A cross-site form cannot send one (origin check). Fields are bounded (200 and 500 characters, control characters refused) and only ever rendered as text in the console. Reports are leads for staff, never acted on automatically: nothing is revoked or flagged from them, and a case is closed by an OPERATOR with a note. | Low. Someone holding a copy of a code can scan it repeatedly and file one report per scan, within the rate limits; staff weigh reports against the scan facts and anomalies shown beside them. |
| **U. Account takeover through the assisted recovery** (someone impersonates a customer to ORBES Client Services to get a recovery code, or guesses one; then takes the account's pieces) | An ADMIN issues a code only after an identity check (SECURITY-MODEL §3.3), audited `account.recovery_code.issue`. The code is 60 bits, stored as an scrypt hash, valid 30 minutes, used once, one open per account; guessing gets 5 wrong guesses per code per hour (attempts while no code is open spend nothing), and the same answer as an unknown email. A recovery ends every session of the account, cancels its pending transfers, withdraws its open links to ownership certificates (THREAT Y) and **pauses new transfers out of it for 72 hours** (`409 TRANSFERS_PAUSED`), so the pieces cannot be handed on at once; the owner, who can no longer sign in, has three days to reach Client Services, which can then lock the account (A-06: its sessions end, its pending transfers are cancelled, its certificate links are withdrawn, its open recovery code is revoked so that a code obtained by a fooled check does not work after the unlock, sign-in and recovery are refused until it is unlocked) while the case is resolved. Every step is audited by account id. | Medium, as for any human recovery process: an identity check that is fooled gives the account for at least the 72 hours of the pause, and the pieces after it if nobody notices. Mitigated by a written procedure (with counsel) and the audit trail; the console shows a paused account (*Transfers paused until …*). Someone who knows an email can also spend the 5 guesses of a code during the 30 minutes after it is issued, so that it fails for the real customer; Client Services sees it (*Recovery attempts throttled until …*, the `account.recover_failed` entries naming the code) and issues a new one, which starts afresh: the block lasts as long as the attacker keeps hitting each new code within its 30 minutes (accepted). A password change or a sign-in with the old password that was under way when the customer's recovery committed is refused (SECURITY-MODEL §3.3), so a hijacked session cannot undo the recovery. |
| **V. Malicious seller** (a RETAIL account of the sale mode, A-08: activating pieces that are not sold, laundering diverted stock as sold in a boutique, or reaching beyond the counter) | The role is the lowest: refused by the guard everywhere but the sale mode, the list of points of sale and its own account (probed route by route in `test/api/admin-roles.test.ts`): no issuance, no code, artifact or certificate download, no read of products, scans, owners or warranties, so a seller can neither print an authentic code nor learn who owns what. An activation needs a sale token minted by a scan of that very piece (a code that verifies, 10 minutes, single use, usable by the scanning account only): no warranty starts from a typed or harvested product id, and a token seen over a shoulder is worthless to another account. No token for a piece already sold: its warranty started, or a client account holds it (ALREADY SOLD), or in a service (NOT FOR SALE); and the activation checks those facts again under the piece's row lock, so a client who registers the piece during the token's 10 minutes, a service opened or its code revoked meanwhile still refuses the sale. The point of sale is chosen from the register an ADMIN keeps (inactive ones refused). Every staff scan is an ADMIN_TEST event naming the seller (in the sale mode, and on `/api/v1/verify` from a browser signed in to the console, S-07) and every activation is audited under the seller with the point of sale and the scan, outside the scan-history rules (a seller's scans cannot make a client's piece look suspicious, nor hide among client scans; a finding of the code itself, steps 6–7, is recorded as for anyone, marked `staffScan`, in the sale mode as on `/api/v1/verify`: a validly signed forgery shown at the counter pages as THREAT A's key-compromise alarm). The lookup draws from the `verify` rate budget, so the counter is not a faster way to judge codes than the public route. Nominative accounts with TOTP in production, disabled in one action at a departure. | Medium. A seller holding pieces (the stock of the boutique) can start the warranty of a piece that is not sold, or record the wrong boutique: the warranty then runs early, and the piece becomes registrable without a claim code if none was issued. Detection is after the fact: activations by seller and by point of sale in the audit log and the verification events, against the boutique's sales. The sale mode is RETAIL's, OPERATOR's and ADMIN's only: an AUDITOR, though ranked above RETAIL, cannot start a warranty there. Removing a wrong activation is an ADMIN decision (void the warranty). A seller who scans diverted stock from a browser signed in to the console raises no UNSOLD PIECE SCANNED (THREAT W), but each of those scans is an ADMIN_TEST under the seller's name. |
| **W. Diversion of unsold stock** (S-07: pieces stolen in stock or in transport, labels or certificate cards taken before the sale, then sold or copied as ORBES pieces) | The label of a piece ORBES has not sold yet (ISSUED, or in a pre-sale service, its warranty not started) is genuine, so it still answers **AUTHENTIC**, but nothing about it says sold: the warranty has not started, first registration is closed until a sale, and the verify app's OWNERSHIP tab says the piece has not yet been delivered by ORBES or an authorised retailer. Every scan of such a piece outside a console session records the anomaly `UNSOLD_PIECE_SCAN` (MEDIUM, with the scan's country, once per piece and per UTC day, API §9.7), console name UNSOLD PIECE SCANNED: the earliest sign of diversion, often before the first copy is sold. Its weight is 0, so an honest customer's result never changes because of it. Staff scans (a console session the console would let in) are ADMIN_TEST under the console user and never raise it, so stock checks do not drown the signal; a console session the guard would refuse (temporary password, missing second factor, disabled account) scans as the public. Triage is by people (the console's Anomalies page), never automatic. | Medium. Detection only, after the fact, and only when someone scans: a diverted piece sold without being scanned raises nothing until its buyer scans it. The piece keeps answering AUTHENTIC until an operator acts (a LOST or STOLEN transition, a revocation, THREAT B), and a seller can still start the warranty of a diverted piece, which then reads as sold (THREAT V; the warranty cannot start during a pre-sale service, so a piece never reads as both under warranty and unsold). An insider scanning diverted stock in a browser signed in to the console raises no UNSOLD PIECE SCANNED, but each scan names them (ADMIN_TEST). A boutique that checks its stock on a phone outside the console raises findings to dismiss with a note: stock is checked from the console (the sale mode or a signed-in browser), and a member of the team scans and registers a piece of their own from a browser that is not signed in to it. |
| **X. A transfer code of another piece** (a seller who owns two pieces gives the buyer of the dearer one the code of the cheaper one, keeps the piece sold, then reports it stolen; or anyone holding a code tries it on pieces they did not scan) | F-03: a transfer is accepted only for the piece the recipient scanned, with that scan (API §11.3). The token is checked before the code is read, so naming other pieces with one scan always gives the same `TRANSFER_TOKEN_INVALID`, and nothing is learnt about which piece a code is for. Every acceptance's audit entry names the scan it used. | Low. A scan proves the code's data, not the object (BRAND §4.6): someone holding a photo or copy of the right code can still scan it and receive the transfer, so the buyer should check the piece itself with its code, which the verify app's flow makes the natural order. `TRANSFER_ACCEPT_REQUIRE_PRODUCT=false` (an acceptance assisted by ORBES Client Services, through the API only: no screen of the verify app or the console accepts a transfer without a scan) lifts both checks, for every pending transfer, for codes sent without a piece or a scan; production warns at every start while it is set (an id named without a scan is still compared only after the code is read, so an unknown id and another piece's answer alike and the switch reveals no issued ids). | **Y. An ownership certificate used to mislead** (F-06: a seller shows a valid certificate of a genuine piece and sells another object, a copy; keeps sharing a certificate after selling the piece; edits a PDF; or someone collects certificates to learn who owns what) | A certificate attests the record, never the object, and says so on the page and in the PDF (*It does not attest the object it is shown with: scan the ORBES CODE of an object to check it*); it never says AUTHENTIC (BRAND §4.6). The buyer's own scan of the object, and the transfer bound to that scan (THREAT X, API §11.3), remain the check of the object. Validity is computed at each reading: a certificate ends for good when its ownership period ends (any transfer), when the piece is LOST, STOLEN, REVOKED, COUNTERFEIT_FLAGGED or RETIRED after it was created (read from the status history, so a piece found again does not revive it), at its expiry (90 days at most), or when its owner withdraws it (then a 404 like an unknown link). A link created by whoever took an account over (THREAT U) is withdrawn with every other open link of the account by ORBES Client Services' lock of the account and by an assisted recovery of its password, in the transaction that cancels its pending transfers (audited `ownership.certificate.revoke` with the reason), and stays withdrawn after an unlock. The PDF is a snapshot: it carries the live link, lettered and as an annotation, so an edited or old PDF is caught by checking it. ## 6. Security assumptions

1. Ed25519 (RFC 8032) and SHA-256 are secure. `node:crypto` and `@noble/curves` implement them correctly.
2. Production private keys live in a KMS/HSM or, for the local provider, on a host where only the service user can read the key directory and the encryption key.
3. TLS terminates at a trusted edge. When geo headers are used, they come from that trusted edge and only in the configured mode; in `mmdb` mode the client IP is the one that edge forwarded (`TRUST_PROXY`).
4. The server clock is accurate (NTP). Lifecycle and anomaly windows depend on it.
5. Database operators are trusted for availability. Integrity is monitored (audit chain), not guaranteed.
6. Customers verify on the official ORBES domain.
